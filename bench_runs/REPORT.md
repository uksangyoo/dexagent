# Which finger-coordination abstraction helps coding agents control a dexterous hand?

UR5e + 20-DOF Tesollo DG5F hand in Newton/MuJoCo-Warp, 12 in-hand tasks, 2026-10-21/22.
Raw tables: `RESULTS.md` (generated by `tools/analyze.py`), per-run notes: `QUALITATIVE.md`, films of the best policy per task: `best/<task>/{overview,reference}/film_*.mp4`.

## Short answer

- **The agentic "synergy" is per-finger task-space (fingertip) control, plus a reachability query and closed-loop helpers. It is not a posture basis.** Agents given raw joints or PCA synergies rebuilt a fingertip layer themselves. Agents given every layer used fingertips and never touched synergies.
- **The next missing layer is contact-level feedback.** A grip-force servo (the `force` level, added in phase 2 after agents kept asking for it) made the solvable tasks fast to solve. It did not unlock the hard ones.
- **What blocks the hard tasks is grasp shape, not coordination.** A two-pad pinch on a thin cylinder is unstable however well its force is controlled. Agents also cannot see link geometry or where contacts actually are.
- **Memory shared across agents moved the hard tasks most (phase 3).** Fresh force-level agents that could read all 61 earlier runs got these held-out scores:

  | Task | Phase 3 | Every earlier agent |
  |---|---|---|
  | pen_finger_roll | **6/6** | 0/6 |
  | pen_gravity_pivot | **4/6** | 3/6 at best |
  | scissors | 1/3 on dev, 0/6 held out | 0 |

  They reused earlier agents' helpers and acted on failure notes. Example: an earlier note said the swing axis should be the free hinge, which led to a grip between index and middle. Over a 4-iteration budget, accumulated skills mattered more than the choice of interface.

## Setup

**Levels.** Each agent got one task, one level, a budget of **4 scored iterations** and about 2.5 h of wall clock.

| Level | What the agent commands |
|---|---|
| joints | 20 joint targets |
| fingertips | per-finger pad positions via IK; only run on cube_pinch |
| synergies | 6 PCA coefficients, leave-one-task-out from the expert postures, ~90 % variance |
| contacts | object-frame primitives: grasp, squeeze, rotate, translate, release, tuck, relocate |
| layered | all of the above at once, usage counted; the EigenDexplore analogue (full action space plus a synergy prior) |
| force | layered plus `grip(obj, {finger: N})`, a per-step contact-force servo along the pinch line |

**Iterations.** Each iteration scores the current policy on 3 fresh random starts, at severity 0, 0.5 and 1 (object pose, size, mass and friction ranges, scaled). The stop rule is two consecutive 3/3.

**Held-out test.** The agent's chosen FINAL policy is run on 6 fixed cases: 1 nominal, 2 at severity 0.5 and 3 at severity 1.

**Scale.** 67 agent runs: 12 tasks × 5 levels, 1 fingertips run, and 6 phase-3 runs (section 5). About 800 scored simulations.

### 2. Initial-condition variation mattered little once a task was solved

Dev and test success are flat across severity 0 / 0.5 / 1 at every level. For example, joints scored 0.42 / 0.46 / 0.53 on test and layered 0.42 / 0.42 / 0.44.

The failures are structural: the method doesn't work at all. They are not about robustness to bigger perturbations. The exception is cube_palm. Its contacts and layered policies failed mostly on larger-than-nominal cubes, because those primitives are blind to object size. The force servo removed that sensitivity: 3/3 at every severity, 5/6 held out.

### 3. What agents actually built and used (the "agentic synergy")

**Joints level.** 10 of 12 agents first built fingertip IK or a fitted forward model inside the policy. Seven did it from finite-difference Jacobians on measured pads, and three fitted multilinear or product-of-exponentials models. That calibration cost about 6–13 s of sim and usually one iteration.

**Synergies level.**
- 10 of 12 built a synergy-to-fingertip model or IK on top of the coefficients.
- 11 of 12 reported coupling problems: the needed finger can't move alone, the thumb is unreachable, or the map is nonlinear beyond about 1 sd.
- One (cube_reorient) built a joint layer on top of synergies instead.
- Synergies helped only where a whole-hand 1-D motion fit the task: a grasp-to-open scalar for cube_palm, and a flexion sweep for cap_twist.

**Contacts level.**
- 5 of 12 rebuilt "put this pad here" out of `approach`/`grasp`, and 10 of 12 used `reach` as a planner.
- 7 of 12 hit the same bug: squeeze and release act toward the object origin, which is wrong for pens and plates.

**Layered level (all layers offered), counted from logged calls in the FINAL policy:**

| Layer | Agents using it |
|---|---|
| fingertips | 12/12 |
| arm | 9/12 |
| contacts | 8/12 (2 of them only for `tuck`) |
| joints | 6/12 (preshape and tuck only) |
| synergies | **0/12** |

**Force level:**

| Layer | Agents using it |
|---|---|
| fingertips | 11/12 |
| grip servo | 11/12 |
| arm | 11/12 |
| contacts | 9/12 |
| joints | 6/12 |
| synergies | **0/12** |

So in the RL sense, EigenDexplore's "synergy" is a posture prior that shrinks exploration. For a coding agent the useful prior is a different representation: per-finger Cartesian targets in the palm or object frame, a cheap feasibility query (`reach`), object-frame contact primitives for whole-grasp motions, and closed-loop wrappers. Agents wrote those wrappers themselves (force bands, scorer replicas, stop-on-contact moves) and reused them across phases. They are the "skills" that accumulate over iterations. A posture basis is something agents route around.

### 4. Why the hard tasks fail: grasp shape and observability

The unsolved tasks are pen_finger_roll, pen_pickup_pivot, pen_writing_grasp, scissors and baoding, plus pen_gravity_pivot which only layered partly solved. The analysis puts failures in these categories:

- **Two-pad pinch on a thin or long object (16 of 49 phase-1 runs, 15 of them pen tasks).** The pen squirts sideways or hinges about the pad line. Force control fixes force but not this, because the instability grows with grip force. The fixes agents proposed and never had budget for are a third contact, a tripod or V-cage, or the palm as a fulcrum. The one pen task that was solved, pen_table_slide, was solved with exactly that kind of geometry: a V-cage for contacts, a lean in the bore for force.
- **Hidden geometry (link shapes, palm surface, pad surface versus pad centre).** `reach` checks only pad centres, so agents planned grasps in which links hit the object (cube_reorient, baoding, scissors).
- **The fingertips are thick relative to a 7.5 mm pen lying on the table.** The contacts sit above the pen's equator and wedge it down (pen_pickup_pivot).

**Capabilities agents said were missing** (number of agents):

| Capability | Agents |
|---|---|
| Link or palm geometry / collision-aware reach | 10 |
| Contact location or pad-surface geometry | 9 |
| Object dimensions | 8 |
| Squeeze/release direction toward the object origin is wrong | 7 |
| Force-controlled squeeze | 6, in phase 1, before the force level existed |
| Better arm IK | 6 |

Experts solve several of these tasks (pen_finger_roll 10/10, scissors 7/10). So the hand and simulator can do them; the agents' interface and budget could not reach those strategies in 4 iterations.

### 5. Phase 3: accumulated skills on the six hardest tasks

**Setup.** Six fresh agents, one per task: pen_finger_roll, pen_gravity_pivot, scissors, pen_writing_grasp, pen_pickup_pivot and baoding.
- Level: force.
- Budget: 6 iterations, with their own dev seeds.
- Memory: permission to read every earlier run's notes, policies and per-case logs, plus `QUALITATIVE.md` and a one-page brief of cross-task lessons (`SKILLS_BRIEF.md`).
- These are workdirs `agents/<task>/skills`. This is not a controlled comparison: the agents had more budget, better information and an idle GPU (about 2–4 min per iteration instead of 20).

| Task | Dev per iteration | Held out | Best earlier | What changed |
|---|---|---|---|---|
| pen_finger_roll | 3,3 | **6/6** | 0/6 | Held the pen between the index and middle fingers, squeezed sideways by their abduction joints under the grip servo. The swing axis is now the free hinge, and the palm rotates about the knuckle axis while the fingers counter-rotate. Reused a scorer-replica monitor from pen_finger_roll/force. |
| pen_gravity_pivot | 0,0,3,2,2,3 | **4/6** | 3/6 | Took the layered agent's pivot sequence almost verbatim and added a servo on the hinge pinch, which stopped the grip bleeding. After the arc, a third finger closes into the measured gap (the V-cage idea from pen_table_slide). |
| scissors | 0,0,0,0,1,0 | 0/6 | 0 | First dev pass on scissors by any agent. Reused the contacts and joints agents' lift-and-handover plan; servo-held squeezes survive the lift. |
| pen_pickup_pivot | 000000 | 0/6 | 0 | A force-servoed middle-finger ledge under the stub solved lift-off, which no earlier agent managed. The pen reached 74° of pivot and stood on end once. |
| pen_writing_grasp | 000000 | 0/6 | 0 | Grasp, lift and a valid stroke in most cases; failed only the final hold. A three-pad chuck lets the pen roll sideways. |
| baoding | 000000 | 0/6 | 0 | Best 113° of the 180° needed. The thumb's links fill the half of the palm where the swap has to happen. |

**Which earlier work each agent reused** is in its report and NOTES.md, and it is substantial: whole phase sequences, monitors, mock apis, and failure diagnoses turned into designs.

This is the "self-learning" axis of the original question. Within one agent, more iterations helped little past about 3. Across agents, written notes plus reusable helpers worked like skill updates and opened tasks no single agent could.

## Caveats

- **Small numbers.** 4 iterations and 6 held-out cases per run make per-cell differences of 1–2 cases noise. Pooled level differences on held-out are not significant; only the speed and usage patterns are clear.
- **Changes mid-study.** The study was paused once, and many phase-1 runs were finished by a second agent reading the first agent's notes. The budget was cut from 8 to 4 iterations and the held-out set from 10 to 6 cases partway through. The fingertips level was run only on cube_pinch.
- **Rule deviations, found by the audit in `QUALITATIVE.md`:**
  - 18 agents looked at partial results from killed, uncounted iterations.
  - 2 agents ran two iterations at once.
  - 6 agents fitted models offline from logged api data.
  - 2 agents read the hand's palm mesh bounds.
  - None used private api or forbidden imports.
- **More geometry reads in phase 3:** the phase-3 pen_finger_roll agent read the hand MJCF and mesh bounding boxes for knuckle axes and link widths. Those files were neither allowed nor forbidden by the brief.
- **Problems with the force servo itself**, reported by phase-2 and phase-3 agents:
  - `grip()` treats 0 N as "settled" for targets at or below 0.3 N.
  - It regulates only force magnitude, so it backs off when a spurious contact already reads the target.
  - It is capped silently at its travel limit.
  - Object-frame directions feed the object's motion back into the servo.
  - It acts only along the pinch line, so it gives way to twisting loads.
