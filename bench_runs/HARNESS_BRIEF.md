# Brief: make one task benchmarkable (phase 0)

Context. We are running an ~8 hour study on the UR5e + 20-DOF DG5F-S hand workcell in /home/uyoo/Projects/dexagent: which finger-coordination abstraction (joints / fingertips / synergies / contact primitives, see dexagent/levels.py) lets coding agents write successful policies fastest and most robustly to initial-condition variation. Fresh agents will later write policies for each task from scratch, scored by an independent checker on randomized starts. Your job is to make ONE task benchmarkable. Be efficient: you have about 45 minutes of wall clock, and the GPU is shared with ~10 other agents.

Read first: README.md, dexagent/README.md, dexagent/cases.py, dexagent/bench.py, and the finished example tasks/hand_demos/cube_pinch (`git diff tasks/hand_demos/cube_pinch/scene.py`, check.py, TASK.md). Then your task's scene.py and helpers, and its notes in tasks/hand_demos/README.md or tasks/inhand/README.md.

Deliverables in your task folder:
1. scene.py: draw initial-condition perturbations from `dexagent.cases.current()` (see cube_pinch). Severity 0 MUST reproduce the current nominal scene exactly (CASE.u returns 0 at severity 0). Choose ranges that a real deployment would see and that make the task meaningfully harder but still physically feasible: typically object position +-15-25 mm, object yaw (or roll about its own axis) +-20-30 deg, object size +-10-15 % where the geometry allows, mass +-50 %, and fixture positions moving with the object where there is a fixture (cup, rest, guide block, jar, book). Name every draw (`CASE.u(r, "name")`). Keep the expert routine's logic unchanged; only make the scene constants it reads follow the perturbation. Do not touch dexagent/*.py — if you find a bug there, describe it in your report.
2. check.py: `OBJECTS` (tuple of scored object names) and `Monitor(sim)` with `.step()` (called once per 20 ms control step) and `.result()` -> {"success": bool, "metrics": {...}}. It reads ONLY simulator state (object poses via `sim[name].pose` = xyz + quat xyzw, joint state, contacts if needed) — never the routine's own outcome or variables. Encode the task's intent as the existing routine's success rule does (see its HAND_RESULT / outcome logic), with tolerances a reasonable person would accept, and robust to the perturbation (measure relative to the object's own start pose). Include intermediate-progress metrics (e.g. max lift, max rotation) so a policy author can see partial progress. A policy must not be able to pass by doing nothing or by a trivially different behavior (e.g. just lifting). The bench holds final targets for 1 s and then calls result().
3. TASK.md: same structure as cube_pinch's: goal in plain words, objects with nominal sizes, start state (palm pose, where things are), variation ranges at severity 1, the exact success rule, and any physical facts a policy author needs that are NOT solution hints (e.g. friction combination rule, that the hand has torsional friction). Do NOT describe how the expert solves it (no finger choices, no grasp widths, no tricks from the README notes). The policy authors will not be allowed to read scene.py routines or the READMEs.

Validation (run from /home/uyoo/Projects/dexagent, CUDA_VISIBLE_DEVICES=1 is set by the bench):
  .venv/bin/python -m dexagent.bench tasks/<group>/<task> --cases 0:0 --out bench_runs/expert/<task>/dev
- The expert must PASS at 0:0 (exception: baoding, whose expert currently fails; define its success as the task intent and report the expert's partial-progress metrics). If the expert fails at nominal, your checker is wrong or too strict; fix the checker, not the routine.
- Then run the fixed TEST set (use exactly this):
  .venv/bin/python -m dexagent.bench tasks/<group>/<task> --cases 1000:0,1001:0.5,1002:0.5,1003:0.5,1004:0.5,1005:1,1006:1,1007:1,1008:1,1009:1 --out bench_runs/expert/<task>/test --label expert/test
  Run it once. Do not tune ranges to make the expert pass — expert brittleness under variation is a result. But if a case is physically impossible (object spawned interpenetrating, falls off a fixture before the robot moves), fix the ranges and rerun.
- Optional sanity film: add `--film <camera>` to a single-case run; it writes a contact sheet jpg you can look at with Read.

Final report (short): perturbation ranges, success rule, expert results on the test set (n/10 with per-case metrics summary), anything odd.
